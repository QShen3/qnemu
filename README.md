# QNEmu

[![CI](https://github.com/QShen3/qnemu/actions/workflows/ci.yml/badge.svg)](https://github.com/QShen3/qnemu/actions/workflows/ci.yml)

QNEmu is an emulator that support Nintendo Game Boy and Game Boy Color. It is still under development and plans to support other consoles in the future. The main purpose of this project is to study computer architecture and software design pattern.

![QNEmu running game](doc/play.png)

## Build

Requirements:
- A C++20 compiler (GCC >= 9, Clang >= 12, or MSVC 2019+)
- CMake >= 3.16 (>= 3.20 if you want to use the bundled presets)
- Qt >= 6.2 with Core, Gui, Widgets and Multimedia modules
- Google Test >= 1.10 (only when building the tests)

Build command:

    cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
    cmake --build build

The executable will be available in `build/qnemu/qnemu`. To run the tests:

    ctest --test-dir build --output-on-failure

CMake presets are also available:

    cmake --preset debug
    cmake --build --preset debug
    ctest --preset debug

| Preset     | Description                                  |
| ---------- | -------------------------------------------- |
| `debug`    | Debug build in `build/`                      |
| `release`  | Release build in `build-release/`            |
| `coverage` | Debug build with coverage instrumentation    |
| `analyze`  | Debug build with clang-tidy and cppcheck       |

Useful options (pass them with `-D` when configuring):

| Option                       | Default | Description                                      |
| ---------------------------- | ------- | ------------------------------------------------ |
| `BUILD_TESTING`              | `ON`    | Build the unit tests (requires Google Test)      |
| `QNEMU_WARNINGS_AS_ERRORS`   | `ON`    | Treat compiler warnings as errors                |
| `QNEMU_ENABLE_CLANG_TIDY`    | `OFF`   | Run clang-tidy while compiling                   |
| `QNEMU_ENABLE_CPPCHECK`      | `OFF`   | Run cppcheck while compiling                     |
| `QNEMU_ENABLE_COVERAGE`      | `OFF`   | Instrument the binary and add a `coverage` target |

The coverage report is generated by:

    cmake -S . -B build -DQNEMU_ENABLE_COVERAGE=ON
    cmake --build build --target coverage

This requires `gcovr` on GCC/Clang builds, or OpenCppCoverage on MSVC builds.

On macOS with Homebrew, the dependencies can be installed with:

    brew install cmake ninja qt googletest

On Debian/Ubuntu, install the Qt and Google Test development packages:

    sudo apt install cmake ninja-build qt6-base-dev qt6-multimedia-dev libgtest-dev libgmock-dev

## CPU core

The SM83 core lives in `qnemu/gb/cpu` and is deliberately independent of Qt,
the MMU and the GUI thread:

- `GbCpu` executes one instruction per `step()` and talks to the rest of the
  machine only through `CpuBus` (`read` / `write` / `tick`).
- Every memory access is one machine cycle, so instruction timing is expressed
  directly in the instruction implementation instead of in a separate table.
- `Registers` is a portable plain struct; flags are the usual `Z N H C` byte,
  with no anonymous-union or endianness assumptions.
- Interrupts are handled at instruction boundaries: IME, the EI one-instruction
  delay, IF/IE priority, HALT, the HALT bug and STOP are all part of the core.
- `GbCpuBus` adapts `GbMmu`'s 1 T-cycle `step()` to the CPU's 4 T-cycle bus
  accesses. The GUI thread lives in `Gb`, not in the CPU.

Unit tests for the core are in `tests/gb/cpu/GbCpuTest.cpp` and use a flat
`TestBus`. They cover reset state, flags and arithmetic edge cases, signed
jumps, the SP-relative instructions, interrupt dispatch, the EI delay, HALT,
the HALT bug and STOP.

## PPU core

The PPU is split into three Qt-free pieces under `qnemu/gb/gpu`:

- `GbPpu` owns the dot/line clock, LCDC/STAT/LY/LYC state, OAM DMA, HDMA,
  palette RAM and the frame boundary. Mode 3 length includes fine-scroll,
  window and sprite fetch penalties; OAM DMA has a two-M-cycle startup delay
  and restart handling.
- `PpuMemory` owns the two VRAM banks, OAM and the CGB palette RAM.
- `PpuRenderer` is a stateless scanline renderer: it reads registers and
  memory, writes one row, and returns whether the window was visible. This is
  the part to drive from unit tests with synthetic VRAM/OAM.

STAT interrupts use an edge/blocking line rather than firing on every mode
change. `GbCpuBus` also implements CGB `KEY0`/`KEY1` and double-speed switching,
including halving the number of peripheral dots per CPU T-cycle.

The PPU never touches Qt or `GbCartridgeInterface`. External memory needed by
OAM DMA/HDMA is supplied through a callback, and finished frames are pushed to
`DisplayInterface` as a plain 160x144 `FrameBuffer`. `RasterDisplay` converts
that buffer to a QImage on the GUI side, without blocking the CPU thread.

PPU tests live in `tests/gb/gpu/` and cover:

- background/window tile addressing, signed tile indexes and DMG palettes
- sprite flips, 8x16 tile selection, the 10-object limit, DMG/CGB priority and
  the CGB object-priority mode (FF6C)
- OAM DMA startup/restart/byte timing, HDMA block copies, mode transitions,
  SCX/window/sprite mode-3 penalties, STAT edge blocking, LYC interrupts and
  VBlank frame delivery
- CGB KEY0/KEY1 and double-speed bus timing
- full-frame image comparison against dmg-acid2 and cgb-acid2

## Test ROMs

`gb_test_runner` runs a ROM headlessly with a small test bus (ROM/MBC1, RAM,
timer, IF/IE, serial and a line counter for VBlank). It understands both common
result protocols:

- blargg serial output and the blargg screen console (`Passed` / `Failed`)
- the Mooneye `LD B, B` breakpoint with the Fibonacci register signature

Usage:

    ./build/tests/rom/gb_test_runner path/to/test.gb
    ./build/tests/rom/gb_test_runner path/to/test.gb --model dmg --max-cycles 300000000

    # attach the real PPU (OAM DMA / LY / STAT / VRAM)
    ./build/tests/rom/gb_test_runner path/to/test.gb --ppu

    # attach the APU (sound register/length/sweep tests)
    ./build/tests/rom/gb_test_runner path/to/test.gb --apu --model dmg

    # render frames and compare against a reference PNG
    ./build/tests/rom/gb_test_runner path/to/acid2.gb --frames 10 \
        --compare-image path/to/reference.png

The ROMs are included as git submodules:

    third_party/gb-test-roms/       # blargg, prebuilt ROMs
    third_party/mooneye-test-roms/  # Mooneye, prebuilt ROMs
    third_party/dmg-acid2/          # source + reference image
    third_party/cgb-acid2/          # source + reference image

Initialize them after cloning:

    git submodule update --init --recursive

The acid2 reference images are in the submodules, but the release ROMs are not
stored in git. Fetch them once (SHA-256 verified):

    python3 tests/rom/fetch_acid2_roms.py

The default destination is `build/test-roms/acid2`; use
`-DQNEMU_ACID2_ROM_DIR=...` if the ROMs live elsewhere.

CMake registers a curated CPU/timing/PPU subset automatically when the
submodules are present, so plain `ctest` covers them as well:

    ctest --preset debug -L rom
    ctest --preset debug -L blargg
    ctest --preset debug -L mooneye
    ctest --preset debug -L ppu
    ctest --preset debug -L sound
    ctest --preset debug -L acid2

The acid2 tests render 10 frames and require an exact 160x144 image match.
Use `-DQNEMU_ENABLE_ROM_TESTS=OFF` to disable the curated tests, or
`-DQNEMU_TEST_ROM_ROOT=...` if the submodules live elsewhere. For an additional
directory tree, `-DQNEMU_TEST_ROMS_DIR=...` registers every `.gb` below it.

To run a whole directory tree manually and get a summary:

    python3 tests/rom/run_test_roms.py third_party/gb-test-roms \
        --include 'cpu_instrs|instr_timing|mem_timing'

    python3 tests/rom/run_test_roms.py third_party/mooneye-test-roms/acceptance \
        --include 'ppu/' --ppu

The CPU-only bus still has a tiny LY/VBlank stub; `--ppu` attaches the real
PPU for OAM DMA, VRAM/OAM blocking, STAT/LYC and rendering.

## Play

Just click the executable and load Rom file.

### Hardware model

QNEmu starts as **CGB** by default. The model can be selected from the command
line:

    ./build/qnemu/qnemu
    ./build/qnemu/qnemu --model cgb   # explicit default
    ./build/qnemu/qnemu --model dmg
    ./build/qnemu/qnemu --model sgb

`-m` is accepted as a shorthand. With `cgb`, a CGB cartridge runs in CGB mode
and a DMG cartridge runs in DMG compatibility mode. `dmg` and `sgb` force the
DMG-compatible CPU/PPU path. SGB-specific features (border, SGB command
protocol, SGB palettes) are not implemented yet, so `sgb` currently behaves as
the DMG hardware baseline.

### Audio

The APU implements all four hardware channels:

- **CH1**: pulse wave with duty, envelope, length timer and frequency sweep
- **CH2**: pulse wave with duty, envelope and length timer
- **CH3**: 32-sample 4-bit wave-table channel with 100/50/25% output levels
- **CH4**: LFSR noise with 15-bit/7-bit modes, envelope and length timer

A 512 Hz frame sequencer clocks the length timers at 256 Hz, the CH1 sweep at
128 Hz and the volume envelopes at 64 Hz.  It is driven by the DIV-APU falling
edge, so writing DIV synchronises the APU exactly like the hardware (including
the power-on DIV glitch).  The mixer applies NR51 panning and NR50 master
volume, models the DACs' negative slope, high-pass filters the DC offset like
the hardware's output capacitor, and downsamples to 44100 Hz stereo signed
16-bit samples.  Qt Multimedia plays the samples through a small ring buffer;
when the buffer is full the emulation thread blocks, which also acts as the
emulator's speed limiter.

Unit tests for the channels, frame sequencer, mixer, panning, volume and
sample output live in `tests/gb/apu/` (`-L` filtering is not needed; run
`./build/tests/qnemu_test --gtest_filter='GbChannel*:GbApu*'`).

The headless runner can attach the APU with `--apu`; the curated
`dmg_sound`/`cgb_sound` register, length, trigger, sweep and power tests run
with `ctest --preset debug -L sound`.  Wave-RAM accesses while CH3 is actively
playing (tests 09/10/12) still depend on cycle-exact bus alignment and are not
part of the curated set.
